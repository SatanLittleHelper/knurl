# Knurl F4 — Auth Screen Design

## Scope

F4 покрывает только happy path авторизации на mobile:

- вход по `email` и `password`;
- регистрация по `email` и `password`;
- сохранение access token после успешного ответа backend;
- переход на защищённый `Home`-экран-заглушку.

Вне скоупа F4:

- `refresh token`;
- автологин с валидацией токена на сервере;
- logout;
- bootstrap пользовательских данных после входа;
- полноценный UI Home-экрана.

## Goals

- Дать пользователю минимальный рабочий сценарий регистрации и входа.
- Зафиксировать единый источник auth-state для роутинга.
- Не смешивать UI, сетевые вызовы и запись токена в одном слое.
- Оставить расширяемую основу для будущих `refresh/logout/bootstrap` сценариев.

## User Flow

1. Неавторизованный пользователь открывает приложение и попадает на `/auth`.
2. На экране авторизации выбирает режим `Вход` или `Регистрация`.
3. Вводит `email` и `password`.
4. После успешного запроса приложение сохраняет access token.
5. Auth-state переключается в `signedIn`.
6. Роутер переводит пользователя на `/home`.

## Screen Design

Используется один экран `AuthScreen` с переключателем режимов `Вход / Регистрация`.

Состав экрана:

- переключатель режима;
- поле `email`;
- поле `password`;
- primary-кнопка submit;
- компактный блок сообщения об ошибке под кнопкой.

Тексты primary-кнопки:

- `Войти` для режима входа;
- `Создать аккаунт` для режима регистрации.

Для F4 не добавляются дополнительные элементы вроде `forgot password`, `logout`, подсказок про refresh token или социальных логинов.

## Form Behavior

- `email` обрезается по краям пробелов перед валидацией и отправкой;
- `password` передаётся как введён;
- при локальной невалидности запрос на backend не отправляется;
- во время `loading` поля, переключатель режима и submit-кнопка блокируются;
- после ошибки пользователь остаётся на том же экране и может повторить попытку.

Минимальная клиентская валидация:

- `email` не пустой;
- `email` похож на email;
- `password` не пустой.

## State Model

`AuthController` управляет двумя связанными вещами:

- состоянием экрана авторизации;
- фактом наличия авторизованной сессии для роутинга.

Состояния формы:

- `signedOut` — форма доступна для ввода;
- `loading` — идёт запрос, элементы ввода заблокированы;
- `error` — форма доступна для ввода, есть текст ошибки;
- `signedIn` — токен сохранён, пользователь считается авторизованным.

Для F4 наличие токена в `TokenStorage` считается достаточным признаком авторизации. Проверка действительности токена сервером откладывается на будущую фичу.

## Architecture

### `AuthScreen`

Отвечает только за UI:

- рендер полей;
- переключение между `Login/Register`;
- вызов действий контроллера;
- показ loading и ошибок.

Экран не должен напрямую:

- вызывать HTTP;
- писать токен в storage;
- принимать решения о защищённой навигации.

### `AuthController`

Отвечает за сценарий авторизации:

- принимает действия `signIn`, `signUp`, `switchMode`;
- переводит состояние между `signedOut/loading/error/signedIn`;
- вызывает `AuthRepository`;
- публикует auth-state для роутера.

### `AuthRepository`

Отвечает за интеграцию с backend и storage:

- вызывает `/auth/login`;
- вызывает `/auth/register`;
- маппит ответ в token;
- сохраняет token через `TokenStorage`.

### `AppRouter`

Отвечает за guard маршрутов:

- если токена нет, ведёт на `/auth`;
- если токен есть, ведёт на `/home`;
- прямой заход на `/home` без токена редиректит на `/auth`.

### `HomeScreen`

В рамках F4 это простой защищённый экран-заглушка. Его задача только замкнуть реальный post-auth flow.

## Data Contracts

F4 опирается на существующий backend auth API:

- `POST /auth/login`;
- `POST /auth/register`.

Запросы:

```json
{
  "email": "user@example.com",
  "password": "secret"
}
```

Мобильный слой ожидает минимально достаточный ответ с токеном. Если формы ответа у `login` и `register` различаются, нормализация делается внутри `AuthRepository`, а не в UI.

## Project Structure

Новые элементы в `mobile/lib/features/auth/`:

- `data/auth_repository.dart`;
- `presentation/auth_controller.dart`;
- `presentation/auth_screen.dart`.

Дополнения в shared-слое:

- обновление `mobile/lib/shared/router/app_router.dart` под маршруты `/auth` и `/home`;
- использование существующих `ApiClient` и `TokenStorage`;
- при необходимости добавление небольшого typed-helper поверх текущего HTTP-клиента, без отдельного SDK-слоя.

## Error Handling

Пользовательские сообщения:

- `401` на логине: `Неверный email или пароль`;
- `400` или `409` на регистрации: использовать человекочитаемое backend message, если оно уже пригодно для UI;
- fallback для регистрации: `Не удалось создать аккаунт`;
- сетевые и неизвестные ошибки: `Проблема с соединением. Попробуйте ещё раз.`

Техническое правило:

- backend-специфика маппинга ошибок остаётся в repository/controller;
- `AuthScreen` работает только с готовым текстом ошибки.

## Testing

Минимальный набор тестов для F4:

- unit-тесты `AuthController`:
  - успешный login;
  - успешный register;
  - переход в `loading`;
  - возврат в error-state при backend failure;
- unit-тесты `AuthRepository`:
  - корректный вызов login endpoint;
  - корректный вызов register endpoint;
  - сохранение token после успешного ответа.

Покрытие навигации можно сделать минимально, если текущая тестовая инфраструктура уже это поддерживает. Иначе полноценные router-тесты остаются вне обязательного минимума F4.

## Risks

- Backend может возвращать разные формы auth-response для login и register.
- Слишком раннее внедрение `refresh/logout/bootstrap` размоет скоуп и замедлит реализацию F4.
- Прямая работа UI со storage или HTTP приведёт к лишней связности и усложнит F5+.

## Acceptance Criteria

- Неавторизованный пользователь попадает на `/auth`.
- На одном экране доступны режимы `Вход` и `Регистрация`.
- Невалидная форма не отправляет запрос.
- Успешный login сохраняет token и переводит пользователя на `/home`.
- Успешный register сохраняет token и переводит пользователя на `/home`.
- `/home` недоступен без token.
- Ошибки backend и сетевые ошибки отображаются пользователю понятным текстом.
